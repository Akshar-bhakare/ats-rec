# **Database Architecture**

---

## **A. Overview**

* **MetaDB:** One global MongoDB database for tenant management and global config.
* **Tenant DB:** One MongoDB database per client/tenant, with full data isolation.
* **Panelist/Interviewer support:** Each interview record links assigned panelists (interviewers) and feedback entries.

---

**Purpose:**

* Stores tenants (clients/agencies), global users, and cross-tenant configs.

## **D. Relationships and Notes**

* **MetaDB** does NOT store tenant data, only configuration.
* **Tenant DB** stores all operational data, strictly isolated.
* **Interviewer** is a User with role 'Interviewer' or 'Panelist', only assigned to Interviews and Feedback.
* **Feedback** is linked to Interview and Panelist (User).
* **Agencies** and their Users may only see their submissions/candidates.
* **Reschedule Logs**: Keep all reschedule history per interview for audit.
* **Soft deletes/Status fields** recommended for all collections.

---

## **E. Migration Plan**

### **1. Initial Setup**

* Onboard new client → Insert tenant record in MetaDB with DB URI.
* Create new tenant DB with required collections and indices.
* Insert ClientAdmin user.

### **2. Adding a New Module/Field**

* Use Mongoose’s schema versioning or migration scripts (e.g., [migrate-mongo](https://github.com/seppevs/migrate-mongo)).
* New collections: Create via migration script, or on-the-fly at first use.
* New fields: Use defaults; avoid breaking changes.

### **3. Tenant Data Isolation**

* All backend logic must resolve the correct tenant DB before accessing data.
* Never query across tenants.

### **4. Upgrades**

* MetaDB migrations are simple (single DB).
* Per-tenant DB migrations must be repeatable; write idempotent scripts or use a migration runner that loops through all tenant URIs in MetaDB.

## **C. Migration & Versioning Plan (MongoDB)**

### **1. Collection/Schema Changes**

* Use a `schemaVersion` field in each document or in a `settings` collection.
* For breaking changes:

  * Write migration scripts using Node.js (Mongoose/TypeORM/Prisma for Mongo), or tools like [migrate-mongo](https://github.com/seppevs/migrate-mongo).
  * Versioned migration folders:

    ```
    /migrations
      /001-add-agency-collections.js
      /002-update-candidates-structure.js
    ```
* **On deployment:**

  * Migration script checks current schemaVersion per tenant DB and applies any pending changes in order.
  * Log migration status in MetaDB for traceability.

### **2. Data Backups**

* Before each major migration, backup all tenant DBs and MetaDB.
* Use cloud provider snapshots or `mongodump`.

### **3. Data Seeding**

* Use `seeds` collection or scripts for test/demo data and per-tenant onboarding flows.

### **4. Monitoring**

* Regularly monitor for schema drift across tenant DBs.
* Use automated tools to check indexes, required fields, data health.
