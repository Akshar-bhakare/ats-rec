# **Tenant Resolution Logic & Context Injection**

---

## **A. Objective**

Enable secure, reliable multi-tenant data isolation for a single codebase, multi-database architecture.
**Every API request must be routed to the correct tenant’s DB context based on subdomain, JWT claims, or request headers.**

---

## **B. Supported Tenant Resolution Mechanisms**

| Mechanism      | How it works                               | Use case                       |
| -------------- | ------------------------------------------ | ------------------------------ |
| Subdomain      | Extract tenant code from request subdomain | `acme.yourapp.com` → `acme`    |
| JWT Claims     | Decode JWT for embedded tenant identifier  | Mobile/API, custom auth flows  |
| Request Header | Custom HTTP header, e.g. `X-Tenant-Code`   | Internal/bulk/batch operations |

---

## **C. Backend Middleware/Interceptor Plan**

### **1. Incoming Request: Tenant Extraction**

Order of precedence (per request):

1. **Subdomain:**

   * Parse incoming hostname (e.g., `acme.app.com`).
   * Extract subdomain (`acme`) and match to tenant code in MetaDB.
2. **JWT Claims:**

   * Decode JWT on Authorization header.
   * Look for `tenant` or `tenant_code` claim (issued at login).
3. **Header:**

   * Check for `X-Tenant-Code` or similar.

If all are present, use subdomain as canonical, then JWT, then header.

---

### **2. Validate Tenant**

* Lookup tenant code in MetaDB (`tenants` collection).
* Check tenant status: must be active.

---

### **3. Inject Tenant Context**

* **NestJS Request-Scoped Provider** attaches:

  * `tenantCode`
  * `tenantId`
  * `tenantDbUri`
* Use dynamic DB connection (Mongoose connection per tenant) for all DB access in request scope.

---

### **4. API Layer Enforcement**

* All service/module methods **require tenant context** for any data read/write.
* If context missing or tenant invalid, return 403/400 error.

---

## **D. Implementation Snippet (NestJS Pseudocode)**

```typescript
// Tenant middleware/interceptor
@Injectable()
export class TenantResolver implements NestMiddleware {
  async use(req, res, next) {
    let tenantCode = extractFromSubdomain(req.hostname)
      || extractFromJWT(req.headers.authorization)
      || req.headers['x-tenant-code'];
    if (!tenantCode) return res.status(400).send('Tenant missing');
    const tenant = await metaDb.tenants.findOne({ code: tenantCode, status: 'active' });
    if (!tenant) return res.status(403).send('Tenant invalid');
    req.tenant = {
      code: tenant.code,
      id: tenant._id,
      dbUri: tenant.db_uri
    };
    // Set up tenant DB connection (if not cached)
    req.tenantDb = getTenantDbConnection(tenant.db_uri);
    next();
  }
}
```

## **E. Frontend Context Plan**

* **Subdomain Routing:**

  * Frontend served on `{tenant}.yourapp.com` (preferred for B2B SaaS).
  * At login, tenant code is set as context for API calls.
* **JWT:**

  * JWT contains tenant code for all authenticated API calls.
* **Header:**

  * For special tools (admin consoles, bulk import), send `X-Tenant-Code` as needed.

---

## **F. Security & Validation**

* **Hard Fail** if tenant context not found, or tenant is suspended/deleted.
* **Never allow tenant code to be set by client for subdomain flow.**
  (Only backend resolves based on request hostname.)
* **Audit Log**: All requests log resolved tenant.
